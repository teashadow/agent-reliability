# Аудит disclosure-template (inkwell) — шаблоны H1-репортов

> Невис, 11.08.2026, единица лупа. Оснастка репортинга, НЕ проба (нет подопытных). 🔴 OPSEC:
> внутренние шаблоны; disclosure только по реальному H1-скоупу когда вернёмся; синтетический finding.

## Анализ — что делает

24 шаблона (3 платформы × 8 типов LLM-уязвимостей) с плейсхолдерами `{{...}}`. `renderer.py`
подставляет контекст (severity/cwe/cvss/target/program/payload/response), `cli.py` даёт
`new`/`preview`/`list-*`. H1-шаблоны — полная структура (Summary/Platform/Vulnerability Details/
Steps/PoC/Impact/Remediation/References), bugcrowd/intigriti — компактная («## Details»).
CWE проставляется по типу (`SEVERITY_CWE`).

## Критика — red-team линза (годится ли для реального H1)

Секции H1 на месте, CVSS/CWE есть — костяк добротный. 🔴 **Но главный изъян — прозаические
секции не заполняются находкой.** Fillable-слоты есть только у `{{payload}}`/`{{response}}`;
Summary, Root Cause, Steps, Impact, Remediation — **литеральный каркас** (`[One paragraph: what
is the vulnerability]`, `[Concrete: data exfiltration…]`). Значит репорт, собранный ИЗ реальной
находки, **всё равно** печатает «[One paragraph…]» — а на H1 это мгновенно клеймит черновик как
машинный/low-effort. Урок OCaml (шаблонная структура сама вызывает подозрение) здесь буквален:
защищает не отсутствие структуры (H1-репорты structured по норме), а **живая проза вместо
каркаса**. Каркас хорош как подсказка человеку в ПУСТОМ шаблоне и ядовит в заполненном.

## Критика — полиглот-ЯП линза

Генерация markdown из данных — Python (строки/шаблоны родные). Довод: остаётся в семье, общий
контракт с finding-organizer тривиален. Оставляю Python.

## Критика — архитектор линза (связь с finding-organizer)

Мост УЖЕ есть, но с той стороны: `fo/exporter.render_finding_markdown` импортит `dt.renderer`.
Однако он передаёт только метаданные-слоты — прозу находки в каркасные секции **не вливает** (их
некуда вливать, слотов нет). Недостающий кирпич пайплайна **находка→репорт**: disclosure-template
должен УМЕТЬ принять finding и развернуть его прозу в секции. Схема Finding (fo/models): `title,
platform, program, severity, type, target, description, steps[], impact, cvss, notes`. Нет
`root_cause`/`remediation` — их каркас честно оставляем (данных нет), не выдумываем.

## Синтез — каким должен быть

1. **Пост-заполнение по заголовку секции** (`fill_sections`), а не новые `{{слоты}}` в 24 файлах:
   под `## Summary` подставить `description`, под `## Steps to Reproduce` — нумерованные `steps`,
   под `## Impact` — `impact`. Работает по всем платформам, СОХРАНЯЕТ типоспецифичный каркас-
   подсказку когда находки нет. Заполняем ТОЛЬКО секции, для которых у находки есть данные.
2. **`render_report(platform, type, finding|None)`** — контракт: finding-JSON → валидный markdown.
3. **CLI `from-finding <json>`** — вход из общей БД (файл finding-organizer) → черновик репорта.
4. **Проверка (дифф-тест против чек-листа H1-полей):** из синтетического finding собрать h1-репорт
   и убедиться: (а) все обязательные H1-секции на месте; (б) реальная проза находки присутствует;
   (в) НЕ осталось каркаса под заполненными секциями (`[One paragraph`, `[Concrete:`); (г) нет
   незаполненных `{{...}}`. Мера умеет сказать «нет»: сломанный finding (пустой description) →
   выход честно помечает пропуск, а не тихо печатает каркас как факт.

**Язык: Python. С доводом.**
