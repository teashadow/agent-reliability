# Аудит finding-organizer — трекер находок → зачаток общей БД фреймворка

> Невис, 11.08.2026, единица лупа. Это ОСНАСТКА, не проба: главный критерий — контракт хранилища,
> а не «мера умеет сказать нет». Три линзы, с упором на архитектора.

## Анализ — что делает

Трекер находок баг-баунти. `Finding` (id·severity·platform·program·status·steps·impact·cvss·
target·notes). `store` — JSON-файл на находку (F-001.json), next_id, save/load/list/update_status.
`exporter` — markdown H1-репорт (fallback + попытка внешнего `dt.renderer`). `board` — Textual TUI.
Самый большой инструмент семьи (521 строка) и уже с JSON-хранилищем — по архитектуре это **зачаток
общей БД и первого GUI-узла**.

## Критика — архитектор-фреймворк линза (главная для оснастки)

1. 🔴 **Схема заточена под РУЧНОЙ H1-репорт, не под находки инструментов.** Поля title/program/
   cvss/steps/impact — это отчёт руками. А 10 доведённых инструментов выдают контракт
   `{инструмент, цель, verdict, findings[]}`. Разрыв: инструменты НЕ могут писать в этот store —
   модель другая. То есть БД семьи и трекер живут порознь.
2. 🔴 **Нет моста контракт-инструмента → запись.** Чтобы finding-organizer стал БД фреймворка,
   нужен `ingest(json-отчёт инструмента)`: находка пробы → Finding с source="tool", маппинг
   verdict→severity, вектор→type. Тогда shadow/overreach/…/snare пишут в общую БД.
3. `dt.renderer` — внешняя зависимость (связь с `disclosure-template`), fallback есть — ок.

## Критика — red-team / полиглот линзы

- Red-team: ценность ручного H1-репортинга сохранить (cvss, steps, PoC — нужны для H1). Не ломать.
- Полиглот: оснастка/БД/доска в целевой архитектуре → **Elixir+Postgres+Phoenix LiveView**. Для v0
  (файловый store + Textual) **Python** ок. При сборке оркестратора: БД → Postgres, доска → Phoenix.

## Синтез — каким должен быть (первый кирпич БД)

1. **Расширить схему:** `source` (manual/tool), `tool` (имя инструмента), `raw_verdict` — чтобы
   Finding вмещал и ручной H1-репорт, и авто-находку пробы. Обратная совместимость: старые поля
   с дефолтами.
2. **`ingest_tool_report(json)`** в store: берёт мой общий контракт (`инструмент/цель/verdict/
   findings`), создаёт Finding(и) с source="tool". Маппинг verdict→severity
   (ПРОВАЛ/критический→critical, высокий→high, ВНИМАНИЕ→medium, ПРОШЁЛ→не заносим). Идемпотентно
   по (инструмент+цель+вектор) — повторный ingest того же прогона не задваивает.
3. **CLI `ingest <json>`** — принять отчёт инструмента.
4. **Оставить ручной репортинг** (new/export/board) нетронутым.

## Пруф для оснастки (не «уязвимый/чистый», а СКВОЗНОЙ)

Взять реальный JSON-отчёт одного из 10 инструментов (overreach) → `ingest` → прочитать обратно
через `list/show` → убедиться: находка сохранена, verdict критический → severity critical,
tool=overreach, повторный ingest не задвоил. Это доказывает, что БД принимает находки семьи.

**Язык: Python (v0 файловый store); при оркестраторе → Postgres+Phoenix. С доводом.**
